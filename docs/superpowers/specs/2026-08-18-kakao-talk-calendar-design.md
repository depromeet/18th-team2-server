# 카카오 톡캘린더 일정 등록 API 설계

- 작성일: 2026-08-18
- 개정: 2026-08-19 — 토큰 확보 방식을 클라이언트 pass-through 에서 서버 주도 추가 동의로 변경
- 이슈: [#251](https://github.com/depromeet/18th-team2-server/issues/251)
- 브랜치: `feature/kakao-talk-calendar`

## 배경

사용자가 참여 중인 파티 일정을 본인의 카카오톡 캘린더에 등록할 수 있게 한다.
현재 레포에는 아웃바운드 HTTP 클라이언트가 하나도 없어, 이 기능이 외부 API 연동 패턴의 첫 사례가 된다.

### 개정 사유

최초 설계는 클라이언트가 카카오 SDK 로 액세스 토큰을 받아 헤더로 전달하는 것을 전제했다.
프론트엔드 저장소를 확인한 결과 그 전제가 성립하지 않는다. 로그인은 브라우저를 백엔드의
`/oauth2/authorization/kakao` 로 보내는 서버 주도 방식이고, 카카오 액세스 토큰은 Spring Security 가
받아 폐기한다. 프론트가 로드하는 카카오 JS SDK 에는 공유 기능만 선언돼 있어 토큰을 얻을 경로가 없다.

로그인을 서버가 수행하는 구조에서는 서버가 토큰을 보유하는 것이 표준이다. 이 개정은 토큰 확보 경로만
바꾸며, 일정 조립·등록 이력·동시성 방어·에러 계약은 최초 설계를 그대로 유지한다.

## 범위

**포함**
- 사용자가 명시적으로 요청할 때만 등록하는 온디맨드 엔드포인트 1개
- 같은 파티를 다시 등록하면 기존 카카오 일정을 갱신
- 파티 시작 전까지만 등록·갱신 허용
- 서버 주도 톡캘린더 추가 동의 플로우
- 카카오 토큰 암호화 저장과 만료 시 갱신
- 연동 해제 엔드포인트
- 사유별로 구분되는 에러 응답

**제외**
- 파티 생성·참여 시점의 자동 등록
- 파티 정보 변경 시 캘린더 일정 자동 갱신 — 파티 수정 API 자체가 없어 붙일 트리거가 없다.
  토큰 저장이 이 기능의 전제 조건이므로 이번에 기반만 마련한다
- 암호화 키 회전 자동화, 토큰 접근 감사 로그
- 일정 삭제 API, 등록 상태 조회 API
- 카카오 외 캘린더 제공자

## 핵심 결정

### 서버가 추가 동의를 받고 토큰을 보관한다

로그인을 서버가 수행하므로 토큰도 서버가 갖는다. 클라이언트는 카카오 자격증명을 다루지 않는다.

저장을 택한 결정적 근거는 파티 수정 시 일정을 자동 갱신하는 기능이다. 그때 사용자는 화면에 없으므로
저장된 토큰 없이는 구현 자체가 불가능하다. 저장하지 않는 대안은 등록할 때마다 인가 리다이렉트를
왕복해야 하는데, 그 방식으로는 이 기능을 영영 만들 수 없다.

동의는 카카오가 기억하므로 두 번째부터 동의 화면은 뜨지 않는다. 리프레시 토큰 수명이 2달이고
갱신할 때마다 연장되므로, 사용자는 사실상 최초 1회만 동의하면 된다.

### 클라이언트가 동의 시점을 통제한다

등록 API 는 순수 JSON 을 유지하고, 동의가 필요하면 인가 URL 을 응답에 실어 보낸다.
클라이언트가 그 URL 로 이동시키고 돌아와 등록을 재시도한다.

서버가 동의부터 등록까지 리다이렉트로 이어서 처리하는 방식도 가능하지만 SPA 와 맞지 않는다.
어떤 파티를 등록할지를 OAuth `state` 에 실어야 하고, 콜백에서 등록이 실패하면 그 사유를 쿼리
파라미터로 전달해야 해서 JSON 에러 계약과 별개의 두 번째 에러 채널이 생긴다.

이 계약은 UI 배치를 강제하지 않는다. 프론트는 등록 시점에 인라인으로 동의를 유도할 수도,
마이페이지의 연동 버튼 뒤에 둘 수도 있다.

### 동의 플로우는 로그인 파이프라인과 분리한다

Spring Security 의 `oauth2Login` 을 확장해 registration 을 하나 더 두는 방법 대신,
동의 전용 컨트롤러가 인가 URL 조립·콜백·토큰 교환을 직접 처리한다.

`OAuth2SuccessHandler` 가 "JWT 를 발급한다"와 "캘린더 토큰을 저장한다"를 registration 으로 분기하기
시작하면 연동이 늘 때마다 그 분기가 자란다. 인증(로그인)과 인가(캘린더 권한)는 성격이 다른 일이다.
`state` 생성·검증과 토큰 교환은 정형화된 작업이라 직접 지는 몫이 크지 않다.

### 일정 내용은 서버가 조립한다

클라이언트는 `partyId`만 보낸다. 제목·시간·설명은 서버가 파티 정보로 만든다.
클라이언트가 임의 일정 내용을 보내는 범용 등록 API가 되면 파티와 무관한 일정도 등록 가능해진다.

### 새 `calendar` feature 패키지로 분리한다

`party` 패키지는 이미 UseCase가 30개로 비대하고, 외부 채널 연동은 성격이 다르다.
cross-feature 접근은 `chat` feature가 쓰는 패턴(자기 feature의 port 인터페이스 + `infrastructure/<타feature>`의 어댑터가 상대 Service 호출)을 그대로 따른다.

## API 계약

엔드포인트 다섯 개다. 클라이언트는 카카오 자격증명을 다루지 않는다.
동의 진입과 콜백은 브라우저 내비게이션이라 서비스 JWT 가 실리지 않고, 나머지 셋은 JWT 로 인증한다.

### 동의 URL 발급

`GET /api/v1/me/talk-calendar-connection/consent-url` — 서비스 JWT 로 인증되는 순수 JSON.

요청자의 `userId` 를 담은 티켓을 만들고, 그 티켓이 포함된 동의 진입 주소를 반환한다.
등록 API 가 403 을 낼 때 싣는 `consentUrl` 도 이 엔드포인트가 만드는 것과 같은 값이다.

이 엔드포인트가 따로 필요한 이유는 티켓 발급 경로가 등록 API 의 403 하나뿐이면 마이페이지에서
"톡캘린더 연동하기" 를 먼저 누르는 UI 를 만들 수 없기 때문이다. 그 경로에는 403 이 없다.

### 일정 등록

`POST /api/v1/parties/{partyId}/talk-calendar` — 요청 body 없음.

| 서버 상태 | 응답 |
|---|---|
| 유효한 토큰 보유 | 200, `data` 에 `eventId` 와 `updated` |
| 액세스 토큰 만료, 갱신 가능 | 갱신 후 200 |
| 연동 없음 / 리프레시 만료 / 동의 철회됨 | 403 `KAKAO_CALENDAR_CONSENT_REQUIRED`, `data` 에 `consentUrl` |

`consentUrl` 은 카카오 `authorize` 주소가 아니라 **우리 동의 진입 엔드포인트 주소**다. 카카오 주소를
직접 주면 티켓과 쿠키가 심기지 않아 콜백 검증이 반드시 실패한다. 클라이언트는 카카오 REST 키도
scope 이름도 알 필요가 없다.

티켓이 URL 에 포함되므로 진입 엔드포인트가 사실상 인증된다.

상태 코드를 403 으로 두는 이유는 RFC 6750 이 scope 부족에 403 을 규정하고 있고, 이 의미의
`KAKAO_CALENDAR_CONSENT_REQUIRED` 가 이미 403 으로 존재하기 때문이다. 409 는 이 엔드포인트에서
이미 두 가지 의미로 쓰이고 있어 세 번째를 얹지 않는다. 401 은 프론트의 공통 인터셉터가 세션 만료로
읽어 사용자를 로그아웃시킬 수 있어 쓰지 않는다.

### 동의 진입

`GET /api/v1/kakao-calendar/consent?ticket={티켓}&redirect_uri={프론트 복귀 주소}`

티켓 서명을 검증하고 만료를 확인한다. `redirect_uri` 는 기존 로그인과 같은
`app.oauth2.authorized-redirect-uris` 화이트리스트로 검증한다. 둘 다 통과하면 티켓과 `redirect_uri` 를
쿠키에 담고 카카오 인가 URL 로 리다이렉트한다.

**티켓이 곧 OAuth `state` 값이다.** 별도의 두 값이 아니다. 카카오에 `state` 로 실어 보내는 값과 쿠키에
담아두는 값이 같은 티켓이고, 콜백에서 이 둘을 대조해 CSRF 를 막는다. 티켓 자체는 서명돼 있어
내용(`userId`, 발급 시각)이 위조되지 않는다. 수명은 **5분**이다 — 동의 화면을 거치는 데 충분하고,
탈취되더라도 창이 좁다.

티켓을 서버 메모리가 아니라 쿠키와 서명값으로 다루는 이유는 blue/green 배포에서 콜백이 다른 인스턴스로
도착해도 검증이 성립해야 하기 때문이다.

### 동의 콜백

`GET /api/v1/kakao-calendar/consent/callback`

쿠키의 티켓과 카카오가 돌려준 `state` 를 대조하고, 인가 코드를 토큰으로 교환한 뒤 연동을 저장한다.
쿠키에 담아둔 프론트 주소로 결과를 붙여 돌려보낸다.

| `calendarConsent` | 상황 |
|---|---|
| `granted` | 저장 완료 |
| `denied` | 사용자가 동의 화면에서 거부 |
| `account_mismatch` | 티켓의 사용자와 카카오가 확인해 준 계정이 다름 |
| `expired` | 티켓 만료 또는 위조 |
| `failed` | 토큰 교환 실패 등 그 밖의 오류 |

`denied` 와 나머지를 구분하는 이유는 안내 문구가 달라야 사용자가 다음 행동을 할 수 있기 때문이다.
특히 계정 불일치에 "다른 카카오 계정으로 로그인돼 있습니다" 를 보여주지 못하면 사용자는 동의와 실패를
무한히 반복한다. 동의를 거부한 적이 없는데 `denied` 로 뭉뚱그리면 그 안내가 불가능하다.

**콜백은 동의를 시작한 사용자와 카카오가 확인해 준 계정이 같은지 대조한다.** 카카오 신원만으로 사용자를
찾으면 브라우저의 카카오 로그인 계정이 서비스 로그인 계정과 다를 때(공용 PC, 계정 여러 개, 카카오 세션
잔존) 토큰이 엉뚱한 사용자 행에 저장된다. 그 사용자는 연동했는데도 계속 동의를 요구받고, 계정 주인은
자기 캘린더에 모르는 일정이 등록될 수 있는 상태가 된다.

로그인 콜백은 신원이 없는 상태에서 신원을 만드는 일이라 대조할 기준이 없지만, 추가 동의는 이미 확정된
신원에 권한을 붙이는 일이라 대조할 기준이 있다. 기준이 있는데 대조하지 않는 것은 결함이다.

그래서 `state` 를 서명된 짧은 수명의 티켓으로 만들어 요청자의 `userId` 를 담는다. 콜백에서 티켓의
`userId` 와 카카오가 알려준 `providerId` 로 찾은 사용자가 일치하지 않으면 저장하지 않고 실패시킨다.
카카오 계정에 대응하는 서비스 사용자가 아예 없는 경우도 같은 실패로 처리한다 — 추가 동의는 기존 사용자의
권한을 확장하는 경로이지 가입 경로가 아니다.

동의 진입과 콜백 두 경로는 브라우저 내비게이션이라 서비스 JWT 가 실리지 않으므로 `SecurityConfig` 에서
인증 예외로 둔다. 다만 무방비는 아니다. 진입 경로는 서명된 티켓 검증과 `redirect_uri` 화이트리스트로,
콜백은 쿠키의 티켓과 카카오가 돌려준 `state` 대조로 보호한다. 신원은 티켓이 지정하고 카카오가 확인해 주며,
두 값이 일치할 때만 저장이 성립한다.

### 연동 해제

`DELETE /api/v1/me/talk-calendar-connection` — 저장된 토큰을 지운다.

카카오 쪽 연결 해제(`unlink`)는 하지 않는다. 그것은 앱 전체 연결을 끊어 사용자가 로그인조차 할 수 없게
만들므로, 캘린더 연동만 끊는다는 의도와 맞지 않는다.

카카오에는 항목 단위 동의 철회 API 가 따로 있어 `unlink` 말고도 선택지가 있다. 권한 조회 응답에서
`revocable` 이 true 인 항목만 철회할 수 있으므로, 톡캘린더 항목이 이에 해당하면 로컬 토큰 삭제보다
정확한 해제가 된다. 이번 범위에서는 로컬 삭제만 한다 — 철회 호출이 실패했을 때 로컬 상태와 카카오 상태가
어긋나는 경우를 다뤄야 하고, 그 정합성 설계는 연동 해제 하나를 위해 지금 감당할 몫이 아니다.
사용자가 완전한 철회를 원하면 카카오 계정 설정에서 직접 할 수 있다.

## 처리 흐름

1. Controller가 `userId`와 `partyId`를 UseCase에 넘긴다.
2. `PartyCalendarInfoPort`로 파티를 조회하고, 요청자가 그 파티의 호스트이거나 현재 참여 중인 참여자인지 검증한다. 파티를 나간 참여자(`hasLeft`)는 등록할 수 없다. 아니면 `PARTY_FORBIDDEN`.
3. 파티가 아직 시작되지 않았는지 확인한다. 현재 시각이 `startedAt` 이후면 `TALK_CALENDAR_PARTY_ALREADY_STARTED`.
4. 저장된 연동에서 사용할 액세스 토큰을 확보한다. 만료가 임박했으면 리프레시로 갱신한다.
   연동이 없거나 갱신이 실패하면 인가 URL 과 함께 `KAKAO_CALENDAR_CONSENT_REQUIRED` 로 끝낸다.
5. 등록 이력을 조회한다.
   - 없으면 `event_id`가 빈 행을 먼저 INSERT하고 flush한다. 그 다음 카카오 일정 생성을 호출하고 받은 `event_id`를 채운다.
   - 있으면 카카오 일정 수정을 호출한다.
6. `event_id` 와 갱신 여부(`updated`)를 응답한다.

이미 시작된 파티를 캘린더에 넣는 것은 사용자에게 의미가 없고, 지난 일정을 갱신하는 경로도 필요 없다.
그래서 생성과 갱신 모두 같은 조건으로 막는다. 파티 종료 여부는 따로 보지 않는다. 시작 전 조건이 더 강하기 때문이다.

행을 먼저 넣는 이유는 동시성 때문이다. 더블클릭으로 두 요청이 동시에 들어오면 둘 다 "이력 없음"을 보고 카카오 일정을 두 개 만든다.
UNIQUE 제약이 걸린 행을 카카오 호출보다 먼저 확보하면 두 번째 요청이 그 제약에 걸린다.
카카오 호출이 실패하면 트랜잭션이 롤백되어 placeholder 행도 함께 사라진다.

정확히 말하면 두 번째 INSERT 는 **즉시 실패하지 않고 첫 트랜잭션이 끝날 때까지 대기한다.** InnoDB 는
미커밋 유니크 키에 대한 중복 INSERT 를 블록시킨다. 첫 트랜잭션이 커밋되면 두 번째는 제약 위반으로 409 가
되고, 롤백되면 통과해 자기가 일정을 만든다. 의도한 직렬화는 성립하지만, 그 대기 동안 두 번째 요청이
카카오 응답 시간만큼 DB 커넥션을 쥐고 있다는 점은 커넥션 풀에 부담이 된다.

다만 이 순서가 DB 와 카카오의 정합을 보장하지는 않는다. 카카오 일정 생성이 성공한 뒤 커밋이 실패하면
카카오에는 일정이 남고 이력 행은 사라져, 다음 요청이 일정을 하나 더 만든다. 보상 로직은 두지 않는다 —
사용자가 직접 지울 수 있는 자기 캘린더 일정이고, 발생 조건이 좁기 때문이다.

이력이 이미 있는데 사용자가 카카오 앱에서 일정을 지운 경우에는 INSERT 가 없어 UNIQUE 제약이 개입하지 못한다.
이 경로는 이력 행을 잠그고 읽어(`PESSIMISTIC_WRITE`) 동시 요청을 직렬화한다.

## 토큰 수명주기

연동은 사용자당 한 행이다. 액세스 토큰과 리프레시 토큰, 각각의 만료 시각을 갖는다.
카카오 기준으로 액세스 토큰은 6시간, 리프레시 토큰은 2달이며 갱신 시 만료가 1달 이내로 남았으면
새 리프레시 토큰이 함께 온다. 두 달에 한 번이라도 사용하면 연동은 사실상 계속 유지된다.

갱신은 등록 요청 시점의 지연 방식이다. 별도 스케줄러를 두지 않는다.
만료까지 **60초** 이하로 남았으면 만료로 간주해 갱신한다. 호출 도중 만료되는 경계를 피하기 위한 여유다.

**토큰 확보는 등록 트랜잭션 바깥에서 끝낸다.** 등록 UseCase 의 트랜잭션 안에서 갱신하면 두 가지가 깨진다.

첫째, 갱신 실패 시 "연동을 지운다"가 롤백된다. 403 을 만들려고 예외를 던지면 같은 트랜잭션이 되감기면서
방금 지운 행이 되살아나고, 죽은 자격증명이 남아 매 요청마다 헛된 갱신 요청을 카카오로 보낸다.

둘째, 락 보유 시간이 길어진다. 최악의 경로는 갱신 → 일정 수정(404) → 일정 생성으로 외부 호출이 3회이고,
호출당 최대 7초(connect 2초 + read 5초)라 21초까지 늘어난다. 그동안 연동 행 잠금과 DB 커넥션을 함께 쥔다.

토큰 갱신은 등록과 논리적으로 독립적이므로 별도 트랜잭션으로 분리한다. 등록 트랜잭션이 시작될 때는
유효한 액세스 토큰이 이미 손에 있고, 연동 행 잠금도 그 전에 풀린다.

### 트랜잭션 경계

트랜잭션 단위는 둘이다.

**토큰 트랜잭션** — 연동 행을 잠그고 읽어, 필요하면 갱신 호출을 하고 결과를 저장한다.
외부 호출 1회를 포함하므로 최대 7초다. 갱신 호출을 잠금 바깥으로 빼면 동시 요청 둘이 각자 갱신을 시도해
카카오가 한쪽 리프레시 토큰을 폐기하는 문제가 생기므로, 짧은 외부 호출 하나는 잠금 안에 둔다.
갱신 실패로 연동을 지우는 것도 이 트랜잭션에서 커밋된다. 그래야 등록 쪽에서 예외를 던져도 삭제가 살아남는다.

**등록 트랜잭션** — 등록 이력 조회·선점과 카카오 일정 호출. 연동 행 잠금은 이미 풀린 상태다.

두 구간을 **한 클래스의 메서드로 나누면 안 된다.** 같은 빈 안에서 호출하면 Spring 프록시를 타지 않아
`@Transactional` 이 아예 걸리지 않고, 조용히 실패해서 통합 테스트로도 잘 드러나지 않는다.
바깥 UseCase 는 트랜잭션 없이 흐름만 조합하고, 두 트랜잭션은 각각 별도 빈에 둔다.

여기서 팀 규칙과 긴장이 하나 생긴다. `.claude/rules/layered-architecture.md` 는 `@Transactional` 을
UseCase 에만 두라고 정하는데, 위 구조는 트랜잭션 경계를 가진 협력 객체 둘이 UseCase 바깥에 생긴다.
두 협력 객체를 각각 UseCase 로 이름 붙이면 규칙은 지켜지지만 같은 feature 안에서 UseCase 가 UseCase 를
호출하게 된다. 어느 쪽을 택할지는 구현 전에 팀이 정한다.

파티 조회(흐름 2번)가 등록 트랜잭션 바깥으로 나가면 지연 로딩이 열린 세션 없이 실행될 수 있다.
필요한 값을 조회 시점에 모두 꺼내오는지 확인해야 한다.

갱신에도 동시성 문제가 있다. 같은 사용자의 요청 둘이 동시에 갱신하면 카카오에 갱신 요청이 두 번 나가고,
카카오가 새 리프레시 토큰을 발급하며 기존 것을 폐기하면 한쪽이 무효한 토큰을 저장한다. 연동이 깨져
사용자가 다시 동의해야 한다. 연동 행을 `PESSIMISTIC_WRITE` 로 잠그고 갱신해 직렬화한다.

갱신이 실패하면(리프레시 만료, 사용자가 카카오에서 동의 철회) 저장된 연동을 지우고 동의를 다시 받는다.
죽은 자격증명을 붙들고 있을 이유가 없다.

## 토큰 보관

액세스·리프레시 토큰은 컬럼 단위로 암호화해 저장한다. AES-GCM 을 쓰고 JPA `AttributeConverter` 로
투명하게 처리한다. GCM 은 매번 랜덤 IV 를 쓰므로 같은 평문도 다른 암호문이 되어 암호문 검색은 불가능하지만,
조회 키가 `user_id` 뿐이라 문제되지 않는다.

암호문 앞에 **키 식별자 1바이트**를 붙인다. 키 회전 기능을 만드는 것이 아니라 포맷을 정해두는 것이다.
지금 넣으면 한 줄이고, 나중에 넣으려면 저장된 데이터를 전부 다시 암호화하는 배치가 필요하다.
회전이 필요해지는 시점에 새 키를 다른 식별자로 추가하고 복호화만 두 키를 모두 받아주면 된다.

키는 `app.crypto.token-secret` 으로 시크릿 저장소에 둔다. `app.jwt.secret` 이 이미 그 자리에 있어
키 관리 방식을 새로 만들지 않는다.

JWT 서명 키를 재사용하지 않는 이유는 수명주기가 묶이기 때문이다. JWT 시크릿 교체는 원래 가벼운 작업이지만
(발급된 토큰이 무효가 되고 사용자가 다시 로그인할 뿐), 같은 키로 카카오 토큰을 암호화해 두면 교체하는 순간
저장된 토큰을 전부 복호화할 수 없게 되어 모든 사용자의 연동이 조용히 깨진다. 같은 시크릿에서 키를 파생하는
절충도 이 문제를 풀지 못한다. 파생 키는 원본이 바뀌면 함께 바뀐다.

## 에러 처리

| 상황 | ErrorCode | HTTP |
|---|---|---|
| 연동 없음 / 리프레시 만료 | `KAKAO_CALENDAR_CONSENT_REQUIRED` — 응답에 `consentUrl` 포함 | 403 |
| 카카오가 scope 부족(`-402`) 응답 | 연동을 지우고 위 403 으로 | 403 |
| 저장된 토큰을 카카오가 거부(`-401`) | 갱신을 시도하고, 실패하면 위 403 으로 흡수 | — |
| 카카오 5xx 또는 타임아웃 | `KAKAO_CALENDAR_UNAVAILABLE` | 502 |
| 이미 시작된 파티 | `TALK_CALENDAR_PARTY_ALREADY_STARTED` — 시작된 파티는 등록 불가 | 409 |
| 동시 요청으로 UNIQUE 위반 | 기존 `DataIntegrityViolationExceptionExtensions`로 변환 | 409 |
| 파티 없음 / 비참여자 | 기존 `PARTY_NOT_FOUND` / `PARTY_FORBIDDEN` | 404 / 403 |

사용자가 카카오 앱에서 일정을 직접 지운 경우 수정 호출이 실패한다. 이때는 기존 이력 행을 재사용해
일정을 새로 만들고, 새 일정 ID 로 이력을 갱신한다.

**이 실패가 어떤 응답으로 오는지는 아직 확인되지 않았다.** 최초 구현은 404 로 가정하고 만들었는데,
`kapi.kakao.com` 은 대체로 400·401·403 에 음수 `code` 를 실어 보내는 패턴이라 404 가 아닐 가능성이 있다.
가정이 틀리면 재생성 경로가 통째로 죽는데, 정상 등록·갱신 테스트는 모두 통과하므로 드러나지 않는다.
실제 호출로 응답 코드를 확인해 숫자를 확정한다. 확인 전까지는 재생성 경로가 검증되지 않은 것으로 취급한다.

카카오 에러 규격은 문서에 정의돼 있다. `-401` 은 HTTP 401 로 토큰 오류(존재하지 않음·만료)를,
`-402` 는 HTTP 403 으로 scope 부족을 뜻하며 응답 본문에 `required_scopes` 와 `allowed_scopes` 가 함께 온다.
따라서 매핑을 배포 후에 조정할 필요 없이 지금 확정한다.

`-402` 는 갱신으로 풀리지 않는다. 사용자가 카카오에서 톡캘린더 동의만 철회한 경우가 정확히 이 응답인데,
액세스 토큰 자체는 유효하므로 리프레시를 해도 같은 scope 부족이 반복된다. 이때는 연동을 지우고
다시 동의를 받아야 한다.

클라이언트에 401 을 내려보내지 않는다. 401 을 쓰지 않기로 한 이유(프론트 공통 인터셉터가 세션 만료로 읽어
로그아웃시킨다)가 이 경로에도 그대로 적용되고, 인터셉터는 에러 코드가 아니라 상태 코드만 보기 때문이다.
저장된 토큰이 거부되면 갱신을 시도하고, 갱신도 실패하면 연동을 정리한 뒤 403 으로 수렴시킨다.
`KAKAO_TOKEN_INVALID` 는 어댑터가 카카오 응답을 구분하기 위한 내부 신호로만 남고 클라이언트에 노출되지 않는다.

`KAKAO_ACCESS_TOKEN_REQUIRED`(400) 는 클라이언트가 토큰을 헤더로 전달하던 시절의 코드이므로 삭제한다.

## 외부 API 사용

| 용도 | 엔드포인트 |
|---|---|
| 일정 생성 | `POST https://kapi.kakao.com/v2/api/calendar/create/event` |
| 일정 수정 | `POST https://kapi.kakao.com/v2/api/calendar/update/event/host` |
| 추가 동의 인가 | `GET https://kauth.kakao.com/oauth/authorize` — `scope=talk_calendar` |
| 토큰 교환·갱신 | `POST https://kauth.kakao.com/oauth/token` |

두 호출 모두 `Authorization: Bearer` 헤더를 쓰고, form-urlencoded 바디의 `event` 파라미터에 일정 정보를 JSON 문자열로 넣는다.
생성 응답에 `event_id`가 담겨 온다.

필요한 동의항목은 **`talk_calendar`** 다. 카카오 문서의 표기는 "톡캘린더 및 일정 생성, 조회,
편집/삭제(talk_calendar)" 이며, 팀이 콘솔에서 활성화한 것을 확인했다.

`talk_calendar_task` 는 "톡캘린더 내 할 일 생성, 조회, 편집/삭제" 로 **할 일(task) 전용**이라 이 기능과
무관하다. 초기 설계에 이 키를 잘못 적어두었으므로 인가 요청과 콘솔 설정 모두 `talk_calendar` 로 맞춘다.

## 사용 권한과 공개 범위

톡캘린더 API 는 **사용 권한이 부여된 앱에서만 모든 사용자를 대상으로 동작한다.** 권한이 없는 앱에서는
앱 멤버만 호출할 수 있고 응답 범위도 그 멤버로 제한된다. 쿼터도 권한을 받기 전에는 테스트 수준으로 묶인다.

카카오가 안내하는 순서는 동의항목 설정 → 기능 구현 → 앱 멤버 대상 동작 확인 → [앱] > [추가 기능 신청]
이다. 즉 **구현이 먼저이고 신청이 나중이다.** 개발과 팀 내 검증은 지금 진행할 수 있고, 막히는 것은
일반 사용자 공개다.

비즈 앱 전환과는 별개 항목이므로 둘을 혼동하지 않는다. 배포 일정을 잡을 때 신청 심사 기간을 고려한다.
권한이 없는 상태에서 앱 멤버가 아닌 계정으로 테스트하면 실패하는데, 이것은 우리 코드의 결함이 아니다.

외부 HTTP 호출이 트랜잭션 안에서 일어나는 구간이 있으므로 `RestClient` 에 connect 2초, read 5초
타임아웃을 건다. 카카오가 느릴 때 DB 커넥션과 행 잠금을 붙들고 있는 시간을 제한하기 위함이다.
개별 호출 기준이라 전체 예산이 통제되지는 않으므로, 트랜잭션 경계를 나눠 한 트랜잭션이 품는 외부 호출 수를
줄이는 것으로 보완한다.

## 설정 추가

| 키 | 용도 |
|---|---|
| `kakao.talk-calendar.base-url` | 기본값 `https://kapi.kakao.com`. 테스트에서 오버라이드 |
| `kakao.auth.base-url` | 기본값 `https://kauth.kakao.com`. 토큰 교환·갱신용. 테스트에서 오버라이드 |
| `app.crypto.token-secret` | 토큰 암호화 키. Base64 32바이트. 시크릿 저장소에 환경별로 다른 값 |
| `app.web-base-url` | 일정 설명의 초대 링크 조립. dev·prod 는 프론트 origin, 로컬은 프론트 개발 서버 |

카카오 client-id 와 client-secret 은 새로 추가하지 않는다. 로그인이 쓰는
`spring.security.oauth2.client.registration.kakao` 값을 `ClientRegistrationRepository` 로 읽어 재사용한다.

설정 외에 카카오 개발자 콘솔에서 동의 콜백 주소를 Redirect URI 로 등록해야 한다.
등록하지 않으면 카카오가 `KOE006` 으로 거부한다.

## 테스트 전략

`docs/testing-rules.md`를 따른다.

- `KakaoTalkCalendarAdapter`: `MockRestServiceServer`로 form 바디, 헤더, 에러 매핑을 검증
- `RegisterPartyTalkCalendarEventUseCase`: Port 스텁으로 생성·갱신 분기, 권한 실패, 시작 시각 경계, 일정 404 재시도를 검증
- 통합 테스트: `TestcontainersConfiguration` 경유로 엔드포인트 동작과 UNIQUE 제약을 검증
- 동의 플로우: 루프백 스텁을 카카오 인증 서버로 세우고 진입 → 콜백 → 저장 → 등록까지 한 흐름으로 검증
- 암호화: 저장된 컬럼이 평문이 아님을 실제 DB 에서 확인

단위 테스트만으로는 부족하다는 것이 이번 작업에서 두 번 확인됐다. 카카오 시각 포맷을 잘못 잡은 것과
오류 응답 본문이 유실되던 것 모두 단위 테스트를 통과했고 실제 호출에서만 드러났다. `MockRestServiceServer`
는 응답 본문을 버퍼링하므로 전송 계층의 동작 차이를 재현하지 못한다. 카카오와 주고받는 계약은
루프백 스텁을 세워 실제 HTTP 로 검증한다.

## 착수 전 확인 사항

코드보다 먼저 확정해야 하는 것들이다. 셋 다 틀리면 만든 코드가 통째로 못 쓰게 되거나 일정이 밀린다.

| 확인할 것 | 상태 |
|---|---|
| 톡캘린더 동의항목 키 | **확정** — `talk_calendar`. 콘솔 활성화 완료 |
| 비즈 앱 전환 | **완료** |
| 톡캘린더 추가 기능 신청 | 미확인. 개발은 막지 않으나 일반 사용자 공개 전에 필요 |
| 삭제된 일정 수정 시 카카오 응답 코드 | 미확인. 실제 호출로 확인해야 하며, 재생성 경로가 여기 걸려 있다 |

`@Transactional` 을 UseCase 밖에 두는 문제(트랜잭션 경계 절 참고)는 팀이 정한다.

## 알려진 부채

등록한 뒤 파티에서 나가거나 파티가 삭제돼도 카카오 캘린더의 일정은 그대로 남는다. 카카오에
일정 삭제 API(`DELETE /v2/api/calendar/delete/event`)가 있으므로 기술적 장애물은 없고, 이번 범위에
넣지 않았을 뿐이다. 토큰을 저장하게 되면 사용자가 없을 때도 정리할 수 있으므로 파티 수정·삭제 연동을
붙일 때 함께 다룬다.

동의 플로우가 붙기 전까지 이 API 는 아무도 호출할 수 없다. 프론트엔드에 톡캘린더 연동 진입점과
`calendarConsent` 복귀 처리가 필요하다. 백엔드 배포만으로는 기능이 동작하지 않는다.

`PartyService`에 `requireParty(partyId)` public 메서드를 추가한다. 기존 공개 메서드가 전부 `RealtimeParty` 전용이고 일반 `Party` 조회는 private이기 때문이다.
이러면 `PartyService`의 public 메서드가 8개가 되어 아키텍처 규칙(5개 이내)에서 더 멀어진다. 이번 작업 범위를 넘어서므로 감수하고 넘어간다.
