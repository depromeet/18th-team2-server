### WebSocket (`loadtest/ws-loadtest.js`, 순정 k6 `k6/experimental/websockets`)

| VU | 연결 성공률 | entered avg | entered p95 |
|---|---|---|---|
| 50 | 100% | 127.7 ms | 281 ms |
| 100 | 100% | 151.0 ms | 357 ms |
| 200 | 100% | 240.0 ms | 472 ms |
| 500 | 100% | 431.0 ms | 1,026 ms |
| 1000 | 100% | 970.8 ms | 2,331 ms |

WebSocket은 5단계(50/100/200/500/1000 VU)를 전부 완주했고, 전 구간에서 성공률 100%·`http_req_failed` 0%를 유지했다. `/actuator/health`도 전 구간 UP 상태를 유지했다. 지연시간은 부하 증가에 따라 완만하고 단조롭게 증가했을 뿐, 연쇄 장애나 서비스 중단은 관측되지 않았다.

### 핵심 대비

- **SSE**: VU 50에서 이미 http_req p95가 타임아웃 상한(30s)에 붙는 경고 신호가 나타났고, VU 100에서 HikariCP 커넥션 풀이 완전 고갈되며 서버 전체가 부하 종료 후에도 3분 이상 회복하지 못했다. VU 200 이상은 시도조차 불가능했다.
- **WebSocket**: 동일 환경에서 VU 1000까지 100% 성공률과 우아한 성능 저하(graceful degradation)를 보였다. 붕괴 지점을 관측하지 못했다.

### 원인 분석 (근거: `docs/superpowers/plans/2026-08-18-sse-websocket-load-test-migration.md`, `.superpowers/sdd/2026-08-18-sse-websocket-load-test-migration/progress.md`)

SSE의 `@Transactional` 입장 플로우는 DB 커넥션을 획득하는데, 열려있는 SSE 커넥션이 그 커넥션을 연결 유지 기간 내내 점유하는 것으로 강하게 추정된다 (정확한 코드 라인 단위로 완전히 증명되지는 않았으나, 다음 두 가지가 강한 정황 증거다):

1. `spring.datasource.hikari.maximum-pool-size`를 10 → 80으로 올려도 VU 100에서 동일하게 풀이 고갈됨 — 단순 용량 부족(under-provisioning)이 아님을 배제.
2. 부하 종료 후에도 수 분간 회복되지 않음 — 일시적 경합(transient contention)이 아님을 배제.

즉 **동시 SSE 연결 수 ≈ 동시에 필요한 DB 커넥션 수**가 되어 커넥션 풀 크기에 의해 하드 캡핑되는 구조적 문제이지, 튜닝으로 풀리는 문제가 아니다. 반면 WebSocket의 STOMP 프레임 처리는 응답을 계속 열어두는 방식이 아니라 메시지 단위로 짧게 끝나는 처리이며, 이 구조적 차이가 SSE와 동일한 벽에 부딪히지 않은 이유로 보인다.

## 트레이드오프

| 항목 | SSE (현재) | WebSocket (전환 시) |
|---|---|---|
| 방향성 | 서버→클라이언트 단방향, 클라이언트 발신은 별도 REST(`chat-messages`) | 양방향 단일 커넥션 |
| 확장성 | 단일 JVM 인메모리 레지스트리, 인스턴스 확장 시 브로드캐스트 유실 | 동일하게 `enableSimpleBroker`는 인메모리 — 다중 인스턴스 확장 시 STOMP 브로커 릴레이(RabbitMQ 등) 또는 Redis pub/sub 필요 |
| 재연결 | HTTP 기반, 브라우저 EventSource가 자동 재연결 지원(단, 이 프로젝트는 직접 fetch/POST 사용이라 수동 구현 필요) | 자동 재연결 없음, 클라이언트가 직접 구현 필요 |
| 인증 | 매 연결이 독립 HTTP 요청 — JWT/participantToken을 매번 검증 | 최초 CONNECT 시 1회 인증, 세션 유지 — 세션 하이재킹 방지책 필요 |
| 로드밸런서 | 표준 HTTP, sticky session 불필요 | sticky session(동일 인스턴스로 라우팅) 필요 — 미설정 시 재연결마다 다른 인스턴스로 갈 수 있음 |
| 인프라 복잡도 | 추가 설정 없음 | 헬스체크가 WS 핸드셰이크를 오탐하지 않도록 별도 처리 필요 |
| **동시성 한계 (실측)** | **VU 100에서 커넥션 풀 완전 고갈 후 비회복성 붕괴, VU 200 이상 측정 불가** | **VU 1000까지 100% 성공률, 붕괴 지점 미관측** |

## 전환 시 챙겨야 할 것

1. **다중 인스턴스 확장**: 현재 SSE/WS 모두 인메모리 브로드캐스트라 스케일아웃 시 그대로 못 씀 — Redis pub/sub 또는 외부 STOMP 브로커(RabbitMQ) 전제 필요
2. **로드밸런서 sticky session**: WebSocket 세션은 특정 인스턴스에 고정돼야 함
3. **재연결/네트워크 전환**: 모바일 환경에서 네트워크 전환 시 재연결 로직 클라이언트에 필요
4. **헬스체크**: `/actuator/health`와 `/ws` 핸드셰이크 경로 분리 확인
5. **일반 채팅 메시지 전송/퇴장 브로드캐스트**: 이번 구현은 입장 플로우만 WebSocket으로 만들었음 — 실제 전환 시 `SendChatMessageUseCase`/`LeaveChatUseCase`도 `ChatSseGateway` 직접 의존을 제거하고 전송 방식에 무관한 포트로 리팩터 필요
6. **버그 발견**: `RealtimeParty.MAX_PARTICIPANTS=14`가 서버에서 강제되지 않음 (표시 전용) — 전환과 무관하게 별도 수정 필요

## 결론

**WebSocket 전환을 권장한다.**

이번 실측에서 SSE는 VU 50 단계부터 이미 http_req p95가 30초 타임아웃 상한에 붙는 경고 신호를 보였고, VU 100에서는 HikariCP 커넥션 풀이 완전히 고갈되어 부하 생성기를 멈춘 뒤에도 3분 이상 서버 전체가 응답하지 않는 비회복성 장애로 이어졌다. VU 200 이상은 시도조차 불가능했다. 이는 단순한 성능 저하가 아니라, "동시 SSE 연결 수 = 동시 DB 커넥션 점유 수"라는 구조적 결함으로, 커넥션 풀을 10 → 80으로 8배 늘려도 동일하게 재현되어 튜닝으로 해결되지 않음이 확인됐다.

반면 WebSocket은 동일 환경·동일 시나리오에서 VU 1000까지 5단계 전부를 100% 성공률로 완주했고, `http_req_failed` 0%, `/actuator/health` UP을 전 구간 유지했다. 지연시간(entered p95)은 50 VU의 281 ms에서 1000 VU의 2,331 ms까지 완만하고 예측 가능하게 증가했을 뿐, 붕괴 지점은 이번 측정 범위 내에서 관측되지 않았다.

두 프로토콜 모두 실제 프로덕션 전환 시 다중 인스턴스 확장을 위한 외부 브로커/Redis pub/sub 도입이 필요하다는 점은 동일한 선행 과제로 남아있지만, 그 이전 단계에서 SSE는 이미 단일 인스턴스·로컬 환경에서도 낮은 동시성(VU 100)에 구조적 한계로 무너진 반면 WebSocket은 훨씬 높은 동시성(VU 1000)까지 우아하게 저하되었다. 이 격차는 "언젠가 확장하면 검토" 수준이 아니라 현재 규모에서도 실사용 임계치에 이미 근접해 있다고 볼 근거이므로, WebSocket으로의 전환을 권장한다.

단, 이번 구현은 입장(enter) 플로우에 한정되어 있으므로 실제 전환 시에는 "전환 시 챙겨야 할 것" 항목(특히 채팅 메시지 전송/퇴장 브로드캐스트의 포트 리팩터, sticky session, 다중 인스턴스 브로커 도입)을 반드시 후속 작업으로 진행해야 한다.
