# 비회원 톡캘린더 일정 등록 설계

- 작성일: 2026-10-14
- 이슈: 미등록
- 브랜치: `feature/guest-talk-calendar-registration`
- 선행 설계: [카카오 톡캘린더 일정 등록 API](2026-08-18-kakao-talk-calendar-design.md)

## 배경

파티는 비회원도 참여할 수 있다. 초대 링크로 들어와 롤링페이퍼를 쓰고 실시간 파티에 입장하는 경로가
모두 열려 있다. 그런데 캘린더 등록만 회원 전용이다. 비회원이 버튼을 누르면 로그인을 요구받는다.

로그인을 요구하는 비용이 기능 가치보다 크다. 일정을 받고 싶을 뿐인 사용자에게 서비스 가입을
강요하는 셈이고, 가입 의사가 없으면 그대로 이탈한다. 또한 사용자가 겪는 동의 화면이 두 번이다.
카카오 소셜 로그인에서 한 번, 톡캘린더 추가 동의에서 또 한 번이다.

이 설계는 비회원이 톡캘린더 동의 한 번만으로 파티 일정을 자기 카카오 캘린더에 등록하게 한다.
우리 서비스 가입은 일어나지 않는다.

`talk_calendar` API 심사는 승인됐다. 선행 조건은 해소된 상태다.

## 범위

**포함**

- 비회원이 초대 링크를 가진 상태에서 호출하는 동의 진입 엔드포인트 1개
- 동의 콜백에서 일정을 생성하고 카카오 토큰을 폐기하는 1회성 등록
- 카카오 회원번호 기준 중복 등록 차단
- 사유별로 구분되는 복귀 결과 전달

**제외**

- 비회원이 등록한 일정의 수정 — 토큰을 저장하지 않으므로 사용자가 화면에 없을 때 갱신할 자격증명이 없다
- 비회원이 나중에 가입했을 때 기존 등록을 회원 계정으로 이어받기
- 비회원 등록 취소·삭제 API
- 비회원을 파티 참여자로 집계하기
- 회원 플로우 변경 — 기존 경로는 그대로 둔다

## 핵심 결정

### 카카오 토큰을 저장하지 않는다

동의 콜백에서 받은 액세스 토큰으로 그 자리에서 일정을 만들고 토큰을 버린다.

비회원의 카카오 자격증명을 장기 보관하지 않는 것이 이 결정의 핵심 이득이다. 회원은 리프레시 토큰을
두 달간 보관하는데, 가입하지 않은 사용자에게 같은 수준의 보관을 적용할 근거가 약하다.
`kakao_calendar_connection` 테이블을 건드리지 않아도 되는 것은 부수 효과다.

대가는 일정 수정 불가다. 파티 시간이 바뀌어도 비회원 캘린더의 일정은 갱신되지 않는다.
회원도 현재 자동 갱신이 없고 파티 수정 API 자체가 없으므로, 이 격차는 당장 드러나지 않는다.

### 식별자는 카카오 회원번호다

비회원에게는 파티 시작 전에 쓸 수 있는 안정적인 식별자가 없다.
`participant_token`은 실시간 파티 입장 시에만 발급되고, 롤링페이퍼로 생긴 참여자 행은 토큰이 없다.
게다가 익명 참여자는 호출마다 새 행으로 저장되어 재방문자를 같은 사람으로 식별할 수 없다.
캘린더 등록은 파티 시작 전 행위이므로 이 경로들이 전부 닫혀 있다.

동의 과정에서 카카오가 확인해 주는 회원번호를 식별자로 쓴다. 이미 회원 동의 플로우가 계정 대조를
위해 같은 값을 받아오고 있고, 회원의 `provider_id`로 저장하고 있는 종류의 데이터다.

### 콜백에서 등록을 끝낸다 — 선행 설계의 기각 결정을 비회원 경로에만 뒤집는다

선행 설계는 서버가 동의부터 등록까지 리다이렉트로 이어 처리하는 방식을 기각했다. 근거는 두 가지였다.
어떤 파티를 등록할지 `state`에 실어야 한다는 점, 그리고 실패 사유를 쿼리 파라미터로 전달해야 해서
JSON 에러 계약과 별개의 두 번째 에러 채널이 생긴다는 점이다.

비회원 경로에서는 두 근거가 성립하지 않는다.

토큰을 저장하지 않기로 했으므로 콜백 이후 재호출할 자격증명이 없다. 등록은 토큰이 살아 있는
콜백 시점에만 가능하다. 선행 설계가 재호출 방식을 택할 수 있었던 것은 토큰을 저장했기 때문이다.

두 번째 에러 채널은 이미 존재한다. 현재 구현도 동의 거부·만료·실패를 쿼리 파라미터로 전달한다.
비회원 결과를 같은 채널에 얹는 것은 채널을 새로 만드는 것이 아니라 기존 채널의 값을 늘리는 일이다.

회원 플로우는 선행 설계의 결정을 그대로 유지한다. 이 결정은 비회원 경로에만 적용된다.

### 권한 근거는 초대 토큰이다

회원은 호스트이거나 참여자일 때만 등록할 수 있다. 비회원은 참여자가 아니므로 이 검증을 쓸 수 없다.
대신 초대 링크 보유를 권한 근거로 삼는다. 롤링페이퍼 작성이 이미 같은 방식이다.

### 비회원을 참여자로 집계하지 않는다

캘린더 등록은 파티 참여 의사 표시가 아니라 일정 알림 수신이다. 참여자 행을 만들면 닉네임도 프로필도
없는 행이 호스트의 참여자 목록과 인원 수에 섞인다. 등록만 한 사용자는 참여자로 세지 않는다.

## 플로우

| 단계 | 경로 | 비고 |
|---|---|---|
| 1 | 초대 페이지에서 캘린더 버튼 | 버튼은 지금도 비회원에게 노출된다 |
| 2 | 동의 진입 URL 요청 — `GET /api/v1/party-invites/{inviteToken}/talk-calendar/consent-url` | 신규, 인증 예외 |
| 3 | 동의 진입 → 카카오 | 기존 경로 그대로 |
| 4 | 카카오 동의 → 콜백 | 기존 경로에 분기 추가 |
| 5 | 결과를 쿼리 파라미터로 실어 초대 페이지 복귀 | 기존 채널 |

4단계에서 비회원이면 토큰을 교환하고 회원번호를 확인한 뒤, 중복을 검사하고 일정을 만들고 토큰을 버린다.

기존 진입 경로가 쿼리로 받은 티켓을 쿠키에 기록하고 콜백에서 `state`와 대조하는 위조 방어를
그대로 물려받는다. 복귀 주소의 origin이 서버 설정이라는 점도 변하지 않는다.

## 티켓 구조

현재 동의 티켓은 사용자 번호와 발급 시각을 담고 서명한다. 비회원은 사용자 번호가 없으므로
주체 종류를 구분하는 접두사를 붙이고, 검증 결과로 회원 번호 또는 초대 토큰을 돌려준다.

티켓 수명이 5분이라 배포 순간 진행 중인 티켓만 무효가 된다. 선행 설계도 같은 이유로 서명 키 교체를
감수할 수 있다고 판단했다. HMAC 서명과 수명 검증은 변경하지 않는다.

## 컴포넌트

UseCase를 둘로 나눈다. 토큰 교환·회원번호 확인과 등록을 한 클래스에 넣으면 생성자 의존성이
여섯 개가 되어 레이어드 규칙의 다섯 개 제한을 넘는다.

| 클래스 | 책임 | 의존성 |
|---|---|---|
| 동의 교환 UseCase (신규) | 인가 코드를 액세스 토큰과 회원번호로 바꾼다 | 2개 |
| 비회원 등록 UseCase (신규) | 초대 토큰·회원번호·액세스 토큰으로 일정을 등록한다 | 4개 |

회원의 동의 저장 UseCase는 변경하지 않는다. 두 신규 클래스는 비회원 경로에서만 쓴다.

콜백 컨트롤러가 둘을 순서대로 호출한다. 기존 등록 컨트롤러가 이미 같은 구성을 쓰고 있고,
한 빈 안에서 나누면 자기호출이라 프록시를 타지 않아 트랜잭션이 걸리지 않는다는 이유가 주석에 남아 있다.
외부 호출을 트랜잭션 밖에 두는 것도 기존 토큰 확보 UseCase와 같은 구조다.

## 스키마

`calendar_registration` 한 테이블만 바꾼다. 마이그레이션 파일은 하나다.

| 변경 | 내용 |
|---|---|
| `user_id` | NOT NULL 해제 |
| `kakao_provider_id` | 추가, 길이 100, nullable. 회원의 `provider_id`와 같은 타입 |
| 유니크 인덱스 | `kakao_provider_id`·`party_id`·`provider` 조합 추가 |

회원 행은 `kakao_provider_id`가 비고, 비회원 행은 `user_id`가 빈다. MySQL 유니크 인덱스는 NULL
중복을 허용하므로 기존 유니크와 새 유니크가 서로 간섭하지 않는다. 기존 데이터는 모두 회원 행이라
마이그레이션으로 깨지는 행이 없고, 컬럼 추가와 NOT NULL 해제만 있으므로 롤백도 가능하다.

`kakao_calendar_connection`은 변경하지 않는다.

## 에러 계약

복귀 결과 enum에 네 값을 더한다. 리다이렉트 기반이므로 이 enum이 사용자에게 사유가 전달되는 채널이다.

| 값 | 상황 | 클라이언트 처리 |
|---|---|---|
| 등록 완료 | 일정 생성 성공 | 성공 안내. 등록 API를 재호출하지 않는다 |
| 이미 등록됨 | 중복 유니크 충돌 | 이미 등록했다고 안내 |
| 파티 시작됨 | 시작 시각이 지났다 | 등록할 수 없다고 안내 |
| 초대 무효 | 초대 토큰이 없거나 만료 | 링크를 다시 받으라고 안내 |

기존 승인 값은 회원 전용으로 남긴다. 클라이언트가 두 값을 구분해 등록 API 재호출 여부를 결정한다.
비회원 복귀 시 재호출하면 일정이 두 번 생성되거나 중복 유니크에 걸리므로 이 구분이 필요하다.

카카오가 권한 거부를 반환하는 경우는 기존 실패 값으로 흡수한다. 심사가 승인됐으므로 상시 상황이 아니다.

## 보안

회원 경로에는 동의한 카카오 계정이 로그인 계정과 일치하는지 대조하는 검증이 있다. 비회원 경로에는
대조할 계정이 없어 이 검증을 적용할 수 없다. 대신 네 겹이 남는다.

| 보호 | 막는 것 |
|---|---|
| 서명된 티켓 | 초대 토큰 위조·변조 |
| 쿠키와 `state` 대조 | 교차 사이트 요청 위조 |
| 초대 토큰 보유 | 무관한 파티 등록 |
| 회원번호 기준 유니크 | 중복 등록 |

남는 위험은 초대 링크가 유출됐을 때 링크를 가진 누구나 자기 캘린더에 그 파티 일정을 넣을 수 있다는
점이다. 롤링페이퍼 작성이 이미 같은 위험 모델이고, 등록되는 내용이 초대 링크로 이미 공개된 정보라
추가 노출이 없다. 회원 경로의 계정 대조는 그대로 유지한다.

## 테스트

| 대상 | 확인할 것 |
|---|---|
| 티켓 서명 | 회원·비회원 티켓 발급과 검증, 종류 혼동 불가, 변조·만료 거부 |
| 비회원 등록 UseCase | 중복 차단, 파티 시작 후 거부, 초대 무효 거부 |
| 콜백 통합 | 비회원 동의가 실제로 일정을 만들고 등록 완료로 복귀하는지, 회원 플로우 회귀 없음 |
| 마이그레이션 | 새 컬럼과 유니크 인덱스 |

카카오 스텁 서버를 재사용한다. 통합 테스트는 기존 컨텍스트 지문에 맞춰 캐시를 깨지 않는다.

## 배포 순서

백엔드를 dev에 먼저 배포해야 프론트가 새 엔드포인트 타입을 받을 수 있다. 프론트의 타입 파일은
dev 문서를 읽어 자동 생성되므로 병렬 작업이 성립하지 않는다.

프론트 작업은 별도 저장소의 다섯 지점이며 이 설계 범위에 포함하지 않는다. UI 컴포넌트는 변경이 없다.
버튼이 이미 비회원에게 노출되고 콜백으로 연결돼 있어 동작만 바뀐다.
